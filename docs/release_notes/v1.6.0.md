# Garmin Running Data Normalizer v1.6.0

These are the release notes for the v1.6.0 local timezone release. Version
`1.6.0` is the current stable release, published from the release-ready main
source after the v1.6.0 tag, GitHub Release, and Production PyPI publication
gates.

## Added

- `run-all`, `snapshot run-all`, and `normalize-activities` accept
  `--timezone` with an IANA timezone name, such as `America/New_York`. Local
  dates and times derived from UTC or FIT timestamps use that timezone;
  `Asia/Tokyo` remains the default.
- `doctor --input --timezone` checks that the selected timezone's data is
  available.
- The timezone used is recorded as `local_timezone` in `run_manifest.json`,
  `run_summary.json`, and `ANALYSIS_CONTEXT.json`, and `START_HERE.md` and
  `ANALYSIS_HANDOFF.md` state it. `validate-handoff` requires the three
  records to agree. The External-safe Pack and the Support Bundle do not
  include the timezone name.
- A name that is not an exact IANA timezone name stops with `TIMEZONE_INVALID`
  (exit 2) before any input is read. Use the Area/Location form, because
  legacy aliases such as `Japan` are not available on every system.

## What the timezone changes

The timezone applies to Activity `activity_datetime_local` and
`activity_date_local` (and therefore the External-safe Pack month), FIT session
`start_datetime_local` and lap `start_time`, Sleep `sleep_start_local` and
`sleep_end_local` (and `sleep_day` when the source has no `calendarDate`), and
the dates of FIT-derived HRV values. Garmin-provided `calendarDate` values are
used as provided and are not shifted.

For example, a run that starts at 20:00 on 2024-01-01 in New York (01:00 UTC
on 2024-01-02) is dated 2024-01-02 by default, because it is 10:00 on
2024-01-02 in `Asia/Tokyo`. With `--timezone America/New_York`, it is dated
2024-01-01.

- One timezone applies to the whole run, so an activity recorded while
  travelling uses the run's timezone. Garmin's per-activity `startTimeLocal`
  is retained as `start_time_local_raw` but is not used.
- A Sleep row without `calendarDate` takes its day from its end time in the
  run's timezone, so the same Export can complete in one timezone and stop
  with `DAILY_METRICS_CONFLICT` in another. FIT-derived HRV values that share
  a local date with different values become review rows.
- Snapshot Stores do not record the timezone, and the canonical build does not
  depend on it; `snapshot run-all --timezone` applies it to the Run-All step.

## Output changes

Rerun Run-All after upgrading. Compared with v1.5.0:

- Without `--timezone`, normalized datasets, analysis tables, QA, and audit
  outputs from the same Export are unchanged. `run_manifest.json`,
  `run_summary.json`, and `ANALYSIS_CONTEXT.json` add `local_timezone`,
  `START_HERE.md` and `ANALYSIS_HANDOFF.md` add the timezone lines, and
  `product_version` `1.6.0` and the digests that include these files change.
- `normalize-activities` adds `local_timezone` to its `run_manifest.json`.
- `validate-handoff`, `doctor --run-output`, and `support-bundle` accept an
  output that contains `diagnostics/` only when the installed version produced
  it, so rerun Run-All for outputs produced by v1.5.0 or earlier.

## Compatibility

- The 17-dataset, 212-field, 6-relationship inventory, stable keys, and output
  paths are unchanged.
- The Snapshot lifecycle contract and policy registry versions remain `v1.0`;
  existing Stores load and verify without migration.
- The Product exit mapping remains `PASS -> 0`,
  `PASS_WITH_WARNINGS -> 0`, `PARTIAL_SUCCESS -> 3`, and `Fatal -> 2`;
  `TIMEZONE_INVALID` is a Fatal result.
- `PARTIAL_SUCCESS` / exit 3 is a completed result with bounded FIT exclusions,
  not a Fatal result.
- Windows keeps the conditional `tzdata` dependency.

See [Known Limitations](../known_limitations.md#local-dates-and-times).

## Install

```bash
python -m pip install garmin-running-data-normalizer==1.6.0
garmin-running-data-normalizer --version
```
